# Общие условия backlog

[Индекс и порядок реализации](../BACKLOG.md). Пути к коду в карточках отсчитываются от корня репозитория.

Дата составления: 2026-09-23. Это план дальнейшей работы, не отчёт о реализации.
Создание backlog не разрешает запуск backup, изменение VPS, переключение доменов
или выполнение перечисленных ниже задач.

## Основание и результат проекта

Источники: [дизайн](../vps3xui-executable-tool-design.md),
[описание проекта](../AGENTS.MD), [handoff](../handoff.md),
[аудит P0](../docs/agent-work/p0/FUNCTIONALITY-AUDIT.md), текущие модули и тесты.
В репозитории описание проекта называется `AGENTS.MD`; ссылка учитывает этот регистр.
Историческая процедура `references/backup-restore.md` даёт контекст, но не
заменяет контракт CLI и проверяемую реализацию.

**P0:** безопасный обычный backup с автономным worker, возвратом источника,
проверкой и контролируемым fetch.

**P1:** управляемое восстановление из доверенной копии на отдельной именованной
Linux-цели: `plan -> prepare -> stage -> activate -> verify`, затем разрешённая
активация конкретной автоматизации Certbot после выполнения условий cutover.
На границе каждого этапа можно остановиться, прочитать результат и безопасно
продолжить только ту же доказуемо принадлежащую задаче операцию.

Статусы: **DONE-LOCAL** — реализовано и проверено локально;
**READY** — можно начинать по этому backlog после поручения на реализацию;
**WAIT** — нужны принятые результаты указанных задач;
**EXTERNAL** — нужны внешняя среда, доверенные данные или разрешённое действие;
**DEFERRED** — вне P0/P1. P1-01 и P1-02 выполнены локально (DONE-LOCAL, 2026-09-23); остальные задачи P1 не выполнены.

## Исходный baseline и внешние условия

Последняя зафиксированная проверка: 581 тест PASS, portable drill — 11 PASS,
регрессионные probes R2–R8 PASS. Это исходный baseline, не результат проверки P1.
Не переоткрывать выполненные функции без конкретной регрессии или требования P1.

OPS-01/02 нужны для production readiness. Синтетические аналоги позволяют
разрабатывать интерфейсы и отрицательные тесты P1 до получения реальных данных.

## Правила декомпозиции и параллельной работы

Первой принимается **P1-01** — общий контракт. После него P1-02–P1-10 могут
реализовываться независимо против принятых типов, интерфейсов и fixtures.
Это параллелизм разработки модулей; реальные изменяющие шаги одной restore-job
на хосте выполняются в заданном порядке под общей блокировкой.

- У каждой задачи один владелец кода и собственные тестовые файлы. Пути в карточках
  для новых P1-модулей — предлагаемое размещение, их пока нет.
- Предлагается пакет `vps3xui/restore/` и модуль `vps3xui/certbot.py`; не создавать
  одновременно `vps3xui/restore.py`. Границы подтверждаются в P1-01.
- В карточках `restore/...` означает `vps3xui/restore/...`, а имена существующих
  Python-модулей без каталога — файлы внутри `vps3xui/`.
- Общий контракт и `tests/restore_support.py` принадлежат P1-01. Изменения
  контрактов после старта потоков согласуются и принимаются до обновления потребителей.
- `coordination.py` и `jobs.py` меняет P1-02. Финальную проводку в `cli.py`,
  `errors.py`, `hostops.py`, SSH/remote_ops/release и общие entrypoints делает
  только P1-13 после приёмки потребителей. Другие задачи используют новые
  специализированные модули и не правят эти общие файлы одновременно.
- Общие P0 verifier/archive/manifest helpers переиспользуются. Не копировать
  parser или алгоритм backup из drill. Необходимые изменения общего кода сначала
  выделяются владельцу интеграции, с обратной совместимостью и P0-регрессиями.
- Для нескольких пишущих исполнителей нужны отдельные проверенные workspaces
  с одним baseline, включающим текущие untracked файлы. Checkout одного HEAD
  не содержит текущую реализацию. Чужие изменения не откатывать.
- При будущем делегированном исполнении: по умолчанию один Flash writer;
  два независимых writer допустимы в отдельных workspaces. Остальные готовые
  потоки ждут свободного слота. Объединяет и принимает результаты один интегратор.

Каждый исполнитель сдаёт ограниченный patch, тесты, результаты проверок и
список оставшихся ограничений. Завершение исполнителя означает готовность
к review, а не автоматическую приёмку или разрешение на deployment.

## Выполнение параллельных потоков

Порядок волн и ссылки на задачи находятся в корневом BACKLOG.md.

Внутри волны не требуется ждать завершения всех соседних задач: потребитель
стартует, когда приняты именно его зависимости и они присутствуют в его workspace.
Например, P1-12 может начаться, пока P1-06/07 ещё готовят data/containers.
Его тесты используют принятый activation contract; реальное включение Certbot
всё равно требует фактически выполненных условий на цели.

При двух исполнителях в волне 1 сначала отдать P1-02 и P1-03, затем заполнять
свободные слоты независимыми задачами. P1-04/05/06/07 ведут к stage; P1-08/09/10
ведут к активации и диагностике. Интегратор не меняет файлы активного writer.

## Контракты между потоками

Точная схема фиксируется в P1-01. Минимальные обязательные связи:

| Результат производителя | Потребители | Что обязано быть проверяемым |
| --- | --- | --- |
| Backup/source identity | plan, payload, activate | Backup digest, manifest, версия, происхождение source evidence; недостаток данных не угадывается |
| RestorePlan/target facts | Все изменяющие стадии | Host key, machine-id, роль target, expiry, allowlist ресурсов, ожидаемые изменения своей job |
| Job/step receipt | Все стадии и status | ID, target, backup/plan digest, намерение/результат, ownership, наблюдаемое состояние, исходная ошибка |
| Prepared target | payload/data/containers/guard | Версии/платформа, Docker готов, renewal не запущен, нет конфликтов |
| Verified payload | data/containers/guard | Точный состав, hashes, безопасные архивы, metadata, reference-only исключения |
| Data/containers receipts | stage/activate/verify | Пути, volumes, реальные IDs/mounts/digests, metadata, Fail2ban, контейнеры остановлены |
| Cutover evidence | activate | Source stopped, защита от повторного старта, актуальность/привязка, независимое управление и отдельное разрешение |
| Guard preparation | certbot activate | Проверенные файлы/hooks, target machine-id, cleanup, срок lease, отсутствие перенесённых runtime rules |
| Verification report | CLI и приёмка | Машинные факты отдельно от ручных подтверждений и `not_run`; нет содержимого секретов |

Нельзя выдавать receipt по факту вызова команды без проверки результата.
Нельзя автоматически включать в план изменения, сделанные другой job.

## Матрица приёмки и прослеживаемость

| Требование дизайна | Задачи | Обязательный отрицательный/положительный сценарий |
| --- | --- | --- |
| CLI, JSON, стабильные ошибки (§5) | P1-01, P1-13 | Все шесть команд работают; отсутствие apply и чужие ошибки не раскрывают секреты |
| Plan и идентичность (§6) | P1-01, P1-03, P1-11 | Два alias на source, смена key/machine-id, expiry и stale inputs блокируются до записи |
| Durable state и повторы (§8, §10) | P1-02, P1-11, P1-14 | Обрыв после эффекта, повтор ID, concurrent backup/restore, неизвестная ownership |
| Backup format и извлечение (§9) | P1-05, P1-06, P1-13 | Missing/hash mismatch/unsupported version/traversal/symlink/special file/лимиты tar |
| Prepare (§10) | P1-03, P1-04, P1-15 | Чистая ОС и готовый Docker; отказ неподдерживаемой ОС; timer не стартует при установке |
| Конфликты target (§10) | P1-06, P1-07, P1-11 | Чужие деревья, volume, container и частичная job не перезаписываются |
| Metadata и ссылки (§9–10) | P1-05, P1-06, P1-15 | UID/GID/mode/ACL/xattrs и Let's Encrypt links восстановлены на Linux |
| Digests/Compose/Fail2ban (§10) | P1-07, P1-15 | Registry unavailable, неверная платформа, cwd/PWD/mounts; оба слоя до первого start |
| OAuth и cutover (§10) | P1-01, P1-09, P1-14, P1-15 | Source недоступен, но не остановлен; fencing отсутствует; автоматического rollback нет |
| Guard и firewall (§11) | OPS-02, P1-08, P1-12, P1-15 | Unknown hooks, wrong machine, cleanup failure; UFW reference никогда не применяется |
| Пассивная диагностика (§12) | P1-10, P1-14 | Ответ source вместо target не считается успехом; модель/Telegram/ACME честно not_run |
| Отказы и восстановимость (§14) | P0-A01, P1-14, P1-15 | Реальные timeout/SIGKILL/transport loss, долговечный status и сохранение данных |
| Протокол агента (§13) | P1-16 | Согласование стадий, передача роли и актуальная документация без дублирования алгоритма |

Локальная проверка каждой задачи: её новые unit/integration tests с
`PYTHONPATH=tests:.` и `PYTHONPYCACHEPREFIX` под `/private/tmp`; данные синтетические.
Полный suite, compileall и portable drill обязательны на границе P1-14 и после
исправлений, влияющих на общие P0-инварианты. Не добавлять новый runtime dependency.
Документирование backlog не требует повторного запуска тестов неизменённого кода.

## Вне P0/P1

**DEFERRED:** автоматический DNS cutover и финальное выключение source,
режим финальной копии с остановленным источником, автоматический rollback OAuth,
импорт/общее изменение firewall, retention/prune, расписание backup,
автоматический boot recovery, MCP/HTTP API/daemon и универсальные workflows.

Legacy backup reader — отдельный возможный backlog после определения его
формата и ограничений; P1 не угадывает недостающие поля старых архивов.
Перевод Fail2ban из writable layer в новые mounts и публикация невоспроизводимого
relay image — отдельные изменения, не скрытая часть restore.

Исключение из общего запрета firewall строго ограничено переносом ранее
разрешённого Certbot guard. Отсутствующие цепочки и закрытые порты диагностируются;
они не дают права автоматически перестраивать firewall.
