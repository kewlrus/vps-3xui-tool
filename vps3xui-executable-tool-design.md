# vps3xui: преобразование skill в executable tool

**Статус:** проект интерфейса и реализации; работающей утилиты в этом документе нет. Команды ниже — предлагаемый контракт будущего CLI.

**Основание:** прочитаны все три Markdown-файла из пользовательского `vps-3xui.zip`: `SKILL.md` (158 строк), `references/apps.md` (214 строк), `references/backup-restore.md` (423 строки). Архив описывает снимок от 20.09.2026, а не гарантированно актуальное состояние VPS. Сервер в рамках подготовки документа не опрашивался и не изменялся. Более позднее сообщение владельца о `agent-relay` учитывается как требование к обновлению инвентаря, а не как результат новой live-проверки.

## 1. Итоговое решение

Сделать небольшой CLI `vps3xui` для конкретного стека владельца, а не универсальную платформу управления VPS и не автоматический компилятор любых skills.

```text
Пользователь / coding-агент
          |
          | намерение, согласование, выбор следующего действия
          v
Тонкий SKILL.md -> локальный vps3xui
                         |
                         | SSH с проверкой host key
                         v
                автономный worker на VPS
                         |
                         +-- Docker / Compose
                         +-- systemd
                         +-- архивы и контроль целостности
                         +-- постоянное состояние операции
```

Модель определяет, что разрешено сделать, объясняет риски и разбирает конфликты. Утилита реализует алгоритм, проверяет ограничения и возвращает структурированный результат. Критическая механика backup не требует доступной модели или живой SSH-сессии.

**Реализация первой версии:** Python 3, стандартная библиотека, штатные OpenSSH/Docker/Compose/systemd/GNU tar. Bash — только для небольшого запускающего/аварийного helper, где это действительно упрощает восстановление. Основную логику не размазывать между Python и shell. Нативный бинарник не обязателен: executable tool здесь означает вызываемый программный интерфейс.

Совместимые версии Python, GNU tar, systemd и Docker/Compose фиксируются после испытаний на исходной и тестовой VPS. Отсутствующие зависимости не устанавливаются из `inspect` или `plan`. На новой VPS установка Docker/Compose и Certbot с их зависимостями входит в явно согласованный план развёртывания, как и в исходном skill. Неизвестная ОС или неподдерживаемый способ установки — остановка, не импровизация.

В первой версии не нужны MCP-сервер, HTTP API, постоянно работающий daemon, plugin marketplace, универсальный YAML workflow engine и собственная система распределённых транзакций.

| Диагностика и безопасное чтение метаданных | модуль `inspect` |
| Preflight, остановка, копирование, возобновление сервисов | модуль `backup` и автономный worker |

Важное исправление прежней формулировки: **политику нельзя оставлять только в Markdown.** Объяснение запрета находится в skill, а проверяемый запрет должен исполняться кодом. Например, несуществующая в CLI операция импорта UFW надёжнее инструкции «не вызывай ufw».

### Пробелы, которые нельзя механически скопировать

В `backup-restore.md:59–61` требуется исключить конкурентный запуск Certbot, но пример worker в строках 88–164 сам не реализует блокировку запуска/сохранение состояния его расписания. Требование нужно превратить в исполняемый протокол.

В примере `COMPLETE` создаётся в строке 162 до восстановления сервисов через `ExecStopPost` и до последующей проверки результата. В новой модели метка завершения не должна подменять доказательство успешной операции.

В архиве есть описание и путь `/usr/local/sbin/certbot-http01-guard`, но **нет исходного текста самого установленного helper и его units**. Их нужно получить из доверенного реального backup или отдельным разрешённым чтением сервера, проверить и зафиксировать. Нельзя заново сгенерировать похожий скрипт по описанию и объявить его тем же проверенным механизмом.

Это логические границы; небольшие модули разрешено объединять. Не создавать дополнительные абстракции без второго реального сценария использования.

На VPS исполняемая версия размещается в root-owned каталоге, например `/opt/vps3xui/releases/<version>/`. Изменение этой версии — явно показываемая часть разрешённого `apply`, не скрытый эффект диагностики. Запущенная операция использует закреплённую версию и не переключается на новый код посреди backup.

Состояние операций — `/var/lib/vps3xui/jobs/<job-id>/`. Секретные backup — отдельный каталог `/var/backups/vps3xui/<backup-id>/`. Для каталогов применяется `0700`, для обычных файлов с данными/метаданными — `0600`. Локальные конфигурации машин, runtime state и backup исключаются из git.

Для read-only диагностики без предварительной установки worker локальный CLI может передавать по SSH фиксированный поставляемый probe через stdin, без сохранения файла на сервере. Агент его не генерирует и не редактирует. При отсутствии нужного runtime диагностика сообщает об ограничении, а не устанавливает пакеты.

## 4. Manifest: факты, а не произвольные команды

Использовать JSON с проверяемой схемой: для первой версии это позволяет обойтись стандартной библиотекой Python. Manifest содержит идентификаторы и пути, но не исполняемые shell snippets и не значения секретов.

Разделить три сущности:

- **Inventory manifest:** какие ресурсы ожидаются и что входит в backup.
- **Operation plan:** что конкретная операция собирается сделать на конкретной машине.
- **Backup manifest:** что фактически сохранено в завершённой копии.

Для существующего снимка inventory должен описать:

| Область | Состав и ограничения |
|---|---|
| Compose | проекты `llmproxy` и `panel`; оригинальные Compose-пути и override-файлы |
| Working directory | `/root/panel` для panel; выставлять реальный cwd и `PWD` согласованно, чтобы `$PWD/db` не указывал в staging |
| Контейнеры из архива | `litellm`, `caddy`, `3xui_app` |
| Volumes | `llmproxy_chatgpt_auth`, `llmproxy_caddy_data`, `llmproxy_caddy_config` |
| Bind data | конфигурации `/opt/llmproxy`, `.env`, `/root/panel/compose.yml`, весь `/root/panel/db`, всё `/etc/letsencrypt` |
| Writable layer | только явно заданные `/etc/fail2ban` и `/var/lib/fail2ban` в `3xui_app` |
| Certbot | конкретный helper, cleanup units, drop-in и разрешение активации |
| UFW | сохранить отдельно, никогда не включать в restore приложений |
| Исключения | `telemt` по умолчанию; весь Docker data-root; Docker-образы; runtime lease Certbot |

Пути volumes получать через Docker, не фиксировать `/var/lib/docker/volumes`. В первой реализации поддерживать только явно проверенные локальные volume drivers/options; для сетевого или неизвестного драйвера прекращать операцию, а не применять схему копирования локального каталога автоматически.

### Изменение после снимка: agent-relay

Владелец позднее сообщил о сервисе `agent-relay` в проекте `llmproxy`. Старый список из трёх контейнеров уже нельзя принимать за полный инвентарь.

`inspect` должен выявить сервис и показать отличие от manifest. До подтверждения его фактического container ID, mounts, конфигурации, порядка запуска и способа восстановления образа backup с претензией на полноту блокируется. Имя контейнера нельзя выводить из имени сервиса догадкой.

Особенно проверить происхождение образа relay. Если это локальная сборка без доступной полной ссылки `repository@sha256:...`, вернуть `E_IMAGE_NOT_RESTORABLE`. Не подменять её случайным тегом, не архивировать образы вопреки исходной политике и не строить заново по неизвестному контексту. Публикация образа или согласование другого способа его воспроизведения — отдельное изменение.

При новом mount или сервисе поведение — **fail closed**: `E_INVENTORY_DRIFT`, перечень только безопасных метаданных и остановка. Автоматически добавлять в backup все найденные каталоги тоже нельзя: это непредсказуемо расширяет объём и доступ к данным.

Полнота означает соответствие утверждённому инвентарю приложений, а не доказательство отсутствия любых иных важных данных на VPS. Новые значимые данные в writable layer требуют отдельной классификации.

## 5. Контракт CLI

Все примеры — проектируемые команды.

| Команда | Назначение | Изменения |
|---|---|---|
| `inspect --host HOST` | Инвентарь и безопасные проверки | Нет намеренных изменений состояния приложений |
| `backup plan --host HOST --out FILE` | Предусловия, ресурсы, операции, downtime | Только локальный plan-файл |
| `backup start --host HOST --plan FILE --request-id ID --apply` | Приём и автономный запуск backup | Да, на источнике |
| `job status ID --host HOST` | Состояние принятой операции | Нет |
| `backup verify --host HOST --job ID` | Проверка архивов и исхода source-job | Чтение |
| `backup fetch --host HOST --job ID --destination DIR --apply` | Передача секретной копии в согласованное место | Запись на стороне назначения |
| `backup verify --directory DIR` | Независимая проверка перенесённой копии | Чтение |
| `restore plan --target HOST --backup DIR --out FILE` | Проверка цели и план восстановления | Только локальный plan-файл |
| `restore prepare --target HOST --plan FILE --apply` | Зависимости и подготовка согласованной цели | Да |
| `restore stage --target HOST --plan FILE --apply` | Передача, staging, образы, данные, создание остановленных контейнеров | Да, без запуска приложений |
| `restore activate --target HOST --plan FILE --apply` | Запуск подготовленного стека после проверки отключения источника | Да |
| `restore verify --target HOST --plan FILE` | Пассивная проверка работающего стека | Чтение и разрешённые диагностические запросы |
| `certbot activate --target HOST --plan FILE --apply` | Активация разрешённой автоматизации после выполнения условий | Да |
| `job recover --host HOST --job ID --apply` | Ограниченное восстановление исходного состояния конкретной job | Да |

У каждой команды — `--json`. В JSON-режиме stdout содержит один объект результата, без Docker progress и shell stdout. stderr — ограниченная безопасная диагностика, а не полный вывод дочерних команд. При необходимости подробностей команда возвращает путь к локальному защищённому отчёту, а не печатает его автоматически.

Не добавлять `restore --force`, `firewall apply`, `down -v`, `prune`, общий `remote exec` или передачу произвольного shell-кода через manifest. `recover` не является универсальным запуском контейнеров: он работает только с сохранёнными идентификаторами и действиями своей job.

### Что означает код возврата

`backup start` с exit code 0 означает принятие job, не готовность backup. `job status` с exit code 0 означает, что статус успешно прочитан: сама job при этом может быть `failed`. Для проверки успеха агент обязан читать поле `state`.

`backup verify` возвращает 0 только при успешных обязательных проверках. Тип причины задаётся стабильным `error.code`; числовые ненулевые коды удобно оставить небольшими группами: ошибка контракта, предусловия/конфликт, ошибка исполнения, провал проверки.

Пример ответа на запуск:

```json
{
  "schema_version": 1,
  "command": "backup.start",
  "request_id": "backup-example-001",
  "job_id": "backup-example-001",
  "state": "accepted",
  "operation_complete": false,
  "error": null
}
```

Пример ошибки:

```json
{
  "schema_version": 1,
  "command": "backup.plan",
  "state": "blocked",
  "error": {
    "code": "E_INVENTORY_DRIFT",
    "message": "Обнаружен сервис, отсутствующий в утверждённом manifest",
    "resource": "agent-relay",
    "next_action": "review_inventory"
  }
}
```

Сообщения не должны содержать секреты или рекомендации, которые автоматически исполняются как команды.

## 6. Plan, разрешения и защита от ошибочной машины

`plan` собирает данные без остановки сервисов, создания удалённых архивов, установки пакетов и `docker pull`. План явно показывает изменяемую машину, перечень операций, объём данных, оценку требуемого места и какие клиентские каналы прервутся. Оценка места учитывает архивы, staging и резерв; это не обещание точного времени выполнения.

План связывается с host key, machine-id, ролью source/target, версией tool/manifest, исходным структурным инвентарём, digest набора входных данных и ограниченным сроком действия. Секреты и их потенциально чувствительные отпечатки не публикуются в обычном выводе.

Перед каждым изменяющим этапом tool повторно проверяет идентичность машины и релевантные предусловия под блокировкой. Допускаются только ожидаемые изменения, которые записала эта же restore-job на предыдущих стадиях. Изменения вне плана приводят к `E_PLAN_STALE`, а не к молчаливой адаптации алгоритма.

Для source сохраняется существующий SSH alias `vps-3xui`, строгая проверка известного host key, BatchMode и отсутствие подмены alias. У target отдельный alias. Различие строковых alias недостаточно: два alias могут вести на один хост. Совпадение защищённого идентификатора источника с целью блокирует restore. Один machine-id тоже не считается криптографическим удостоверением машины: используются также проверенный SSH host key и контекст подключения.

**`--apply` не является доказательством согласия человека.** Модель может сама написать этот флаг. Разрешение на изменение/остановку даётся пользователем в управляющей среде; CLI уменьшает вероятность ошибки проверками плана и адресата. Для независимой границы безопасности нужны ограничения SSH/sudo/прав на worker или внешняя система approvals. При сохранённом произвольном root SSH утилита не может запретить обход самой себя.

Разрешения не расширяются неявно: backup источника, deployment названной цели и DNS cutover — разные действия. Установка Docker/Compose и Certbot с необходимыми зависимостями входит в разрешённый deployment. Сохранённое разрешение на конкретный Certbot guard переносится по исходной политике, без повторного согласования того же исключения; оно не даёт права импортировать другие firewall-правила.

## 7. Автономный backup как машина состояний

```text
accepted -> preflight -> quiescing -> copying
         -> recovering -> verifying -> succeeded

ошибка после начала изменений -> recovering -> failed
невозможность восстановить сервисы/таймеры -> recovery_required
неполные доказательства после аварии хоста -> unknown/interrupted
```

### До остановки прокси

Worker и его аварийный helper уже доставлены, проверены и закреплены по версии. Зафиксированы request ID, unit name, исходные container IDs и их состояния, состояние затрагиваемых таймеров, каталог backup и инструкция аварийного восстановления. Никакой установки зависимостей после остановки прокси.

Одна эксклюзивная блокировка на стек защищает от одновременных backup/restore/recover. Предусмотреть также незавершённую job: потеря lock из-за смерти worker не является основанием безусловно начать новую операцию, пока восстановление прошлой не завершено. Блокировка и журнал должны учитывать финализатор, а не только основной процесс.

Preflight проверяет пути, volumes, образы, место, поддерживаемое окружение, активные процессы продления и HTTP-01 lease. При активной lease backup не начинается; cleanup-защита не выключается.

### Certbot и согласованность

После разрешения на backup временно запретить известные автоматические триггеры продления, сохранив исходные active/masked/enabled-состояния. Предусмотреть гонку между первым наблюдением и отключением триггера: повторно убедиться, что продление не началось, до остановки контейнеров. Не прерывать уже работающий Certbot ради получения копии.

Для systemd-варианта можно использовать временное блокирование известных service/timer с последующим точным восстановлением. Конкретный способ требует проверки на установленной версии и учёта всех обнаруженных запускателей. Системная блокировка не останавливает пользователя, который напрямую запускает другой `certbot` из shell: необходимы согласованное окно обслуживания и известный единый путь запуска. При неизвестном scheduler или hook возвращать конфликт.

### Остановка и копирование

Останавливать только утверждённые исходно работающие контейнеры; сохранять их IDs, а не полагаться на повторное появление того же имени. Не запускать ранее остановленный `telemt` или иной сервис. Порядок остановки и восстановления учитывать в manifest, в том числе после включения relay.

Копировать согласованные bind trees и named volumes. Для panel сохранять весь каталог БД, а не только `x-ui.db`. Отдельно сохранить два каталога Fail2ban из остановленного контейнера; не копировать весь writable layer. Проверить, что ни один неучтённый работающий контейнер не продолжает писать в включённый volume/bind.

### Возврат сервисов

Основной workflow возвращает исходно работающие контейнеры сразу после окончания копирования неизменяемого набора данных, не растягивая downtime ради последующего чтения SHA256. Финальная проверка архивов выполняется уже над копией. `ExecStopPost` повторно и идемпотентно обеспечивает восстановление при ошибке/завершении worker.

Использовать service с `Type=exec`, лимитами исполнения и остановки, `KillMode=control-group` и `ExecStopPost`. `systemd-run` запускается без привязки потока исполнения к SSH/model transport. Лимит из старого примера 15 минут не считать универсальным: его задаёт проверенный план операции.

Согласно документации systemd, `ExecStopPost` применяется и при аварийном завершении; ему доступны результат службы и статус основного процесса. Поэтому финализатор сохраняет исходную ошибку отдельно от результата восстановления. Успешный `docker start` не превращает упавший backup в успешный [1, 2].

Это защита от потери модели/SSH и многих отказов worker, но не гарантия при отказе питания, диска, Docker daemon или самого systemd. После перезагрузки незавершённая job не объявляется успешной. Для P0 предусматриваются обнаружение незавершённости и ручной `job recover` через независимый SSH; автоматический boot-recovery — отдельное расширение после испытаний.

## 8. Постоянное состояние и повторные вызовы

Хранить `request.json`, `initial-state.json`, `state.json`, безопасный журнал событий и итоговый отчёт в каталоге job. Обновления критических файлов — атомарная замена с записью на диск; перед первой остановкой запись исходного состояния должна быть завершена. Предусмотреть нехватку места: при невозможности надёжно записать исходное состояние остановка запрещена.

Request ID создаётся локально и сохраняется **до** отправки запуска. Если SSH оборвался до ответа, повтор с тем же ID возвращает существующую job либо безопасно продолжает её регистрацию, а не создаёт второй backup. Тот же ID с другим планом — конфликт. Безусловных retries изменяющих шагов не делать.

Статус должен переживать завершение transient unit. systemd умеет выгружать неиспользуемые units, поэтому отсутствие `--collect` не заменяет собственный долговечный отчёт [3]. Отсутствие unit и отсутствие отчёта — `unknown`, а не `succeeded`.

Итог разделяет как минимум:

```json
{
  "state": "succeeded",
  "data_integrity": "verified",
  "source_runtime_recovery": "verified",
  "passive_proxy_checks": "passed",
  "model_generation": "not_run",
  "telegram_client_test": "not_run",
  "restore_drill": "not_run"
}
```

После переноса backup поле о восстановлении source — исторический отчёт, а не утверждение о текущем состоянии той VPS. Проверка копии на другой машине не требует старого systemd unit.

## 9. Формат backup и проверка

Сохранить узнаваемые имена существующих tar-артефактов. Добавить версионированные `backup.json`, `images.json` и итоговый source-operation report; при необходимости временно оставлять `images.txt` для человека. Читатель legacy backup реализуется отдельно, с явными ограничениями, а не угадывает недостающие поля нового формата.

В metadata включить версии tool/формата, платформу/архитектуру, инвентарь фактически включённых ресурсов, registry digests, сведения о размере/целостности, исключениях и исходном завершении операции. Не помещать секреты в metadata.

`SHA256SUMS` покрывает все неизменяемые артефакты и metadata без циклического хеширования. `COMPLETE` публикуется атомарно только после успешной финализации обычного backup. Неполная копия остаётся помеченной как partial; предыдущие копии и исходные данные автоматически не удаляются.

Проверять не просто «все перечисленные суммы совпали», а точное наличие всех обязательных файлов для данного инвентаря. Отсутствующий в списке обязательный архив тоже ошибка. `SHA256SUMS` и manifest должны ссылаться только на разрешённые относительные пути, без выхода из каталога и без подмены symlink.

До распаковки проверяются эффективные имена и типы tar members, PAX-переопределения, ссылки, дубликаты, размер/количество записей. Не допускать выход за staging, абсолютные пути, опасные special files и запись через подставленные symlink-предки. Не строить security parser на текстовом `tar -tf` и `grep`.

При этом законные ссылки `live -> ../../archive/...` в `/etc/letsencrypt` должны сохраняться. Проверяется конечное разрешение ссылки внутри допустимого дерева, а не запрещается любой `..` в link target. Метаданные владельцев/прав/ACL/xattrs сохраняются и восстанавливаются только в рамках проверенного формата и доверенного состава; не превращать архив в возможность записать произвольные системные capabilities или hooks.

SHA256 — контроль целостности, не независимая аутентификация отправителя. Принимать backup только из доверенного источника; использовать проверенный SSH и согласованное зашифрованное хранение. `backup fetch` не печатает файлы в контекст и не выгружает их в произвольное облако. Совпадение сумм само по себе не доказывает возможность восстановления.

## 10. Restore: подготовка отдельно от активации

**Никакого универсального `restore-everything --yes`.** Стадии завершаются наблюдаемыми результатами и допускают остановку на границе.

`prepare` проверяет именованную цель, её ОС, зависимости, место, registry-доступ и отсутствие конфликтов. Установка пакетов — изменяющий этап. Способ установки Docker выбирается только из поддерживаемых и проверенных адаптеров для конкретной ОС; действующая установка не переустанавливается без причины [6]. При установке Certbot предотвращается преждевременное включение renewal scheduler.

`stage` передаёт backup, проверяет его, распаковывает в новый приватный staging, переносит только утверждённые деревья на отсутствующие пути и восстанавливает volumes. Конфликт `/opt/llmproxy`, `/root/panel`, `/etc/letsencrypt`, контейнера или непустого volume — остановка. Повтор разрешён только для доказуемо принадлежащих той же job шагов, с тем же backup и совпавшим ожидаемым состоянием. Между файловой системой, Docker и systemd нет общей атомарной транзакции: частичное восстановление явно журналируется, а не маскируется словом «идемпотентность».

Образы скачиваются по полным `repository@sha256:...`, с проверкой платформы. У Docker digest позволяет закрепить конкретную версию; mutable tag не эквивалентен такому закреплению [4]. Недоступный digest — ошибка, не повод перейти на `latest`. Образы не включаются в backup, поэтому disaster recovery зависит от доступности соответствующего содержимого в registry.

Контейнер panel сначала создаётся, но не запускается. Данные Fail2ban восстанавливаются в него до первого старта. Это нужно сохранить отдельно от восстановления volumes: Docker удаляет writable layer при удалении контейнера, в отличие от независимого жизненного цикла volume [5]. Последующее пересоздание panel опять потребует переноса этих данных; переход на новые mounts — отдельное архитектурное изменение, не скрытая часть restore.

Для Compose использовать исходные project names и сохранённые digest override-файлы. Рабочий каталог panel выставляется реально; после создания проверяются фактические mounts, а не только синтаксис Compose. Никаких автоматических обновлений моделей, ключей или маршрутов.

### Защита ChatGPT OAuth при активации

Исходный skill запрещает два активных сервера с одним ChatGPT OAuth-хранилищем. Поэтому успешный staging не разрешает немедленно включить вторую LiteLLM.

`restore activate` требует отдельного разрешённого этапа переключения, проверки остановленного источника и независимого пути дальнейшего управления. Недоступность источника по сети не доказывает, что он выключен. Нужны фактическая остановка и организационная/техническая защита от повторного старта на время передачи роли. Флаг CLI не доказывает независимость модельного канала.

Обычный backup всегда возвращает source к исходному состоянию. Режим финальной копии с оставленным остановленным источником — отдельный migration workflow, не добавлять его незаметным `--leave-stopped` к P0. Если нужна актуальная финальная копия, её создание и удержание source остановленным заранее выполняются через независимый канал по отдельному плану владельца. Архивная копия имеет собственную точку восстановления и не становится «финальной» от запуска на target.

Для отката сначала прекращается работа target. Старый `auth.json` нельзя автоматически считать действующим после refresh на новой VPS: возможна необходимость отдельного восстановления авторизации, как указано в исходном skill. Автоматический rollback с молчаливым стартом старого OAuth исключается.

## 11. Certbot и firewall: точное сохранение исключения

UFW-архив и текстовые снимки проверяются и сохраняются как справочные материалы. Они не входят в allowlist извлечения в системные пути, не исполняются через UFW/iptables/nft и не используются как startup hooks. При закрытом порте утилита сообщает о недоступности, не открывает его сама.

Единственное переносимое исключение — конкретный ранее разрешённый `certbot-http01-guard`. После проверки происхождения и состава helper/units разрешение перепривязывается к machine-id target, без копирования machine-id исходной ОС. Runtime lease и временные правила не переносятся. Установить и проверить cleanup-watchdog до активации scheduler продления.

Сохранить заданные текущим skill пределы: lease 900 секунд и проверки cleanup каждые 30 секунд. При отсутствии требуемых firewall chains не создавать UFW и не расширять права автоматически. Отличающуюся существующую автоматизацию не перезаписывать.

`certbot activate` допускается после корректного переключения домена панели, проверки условий HTTP-01 и доверенных hooks. Разрешение на deployment включает восстановление этой конкретной автоматизации, но не запуск любых скриптов из backup. Проверять также directory hooks в `/etc/letsencrypt`, которые будут исполняться при дальнейшем продлении.

`certbot renew --dry-run` — активное обращение к ACME, а не read-only диагностика: документация описывает тестовое получение сертификата и возможное выполнение pre/post hooks [7]. В пассивную проверку оно не входит. Для реальной проверки продления нужен явно разрешённый этап после cutover. Активный timer и отсутствие ошибки у `renew` не приравниваются к подтверждённому успешному циклу обновления.

## 12. Диагностика и защита секретов

Разрешённые проверки по исходному skill: метаданные контейнеров/mounts, безопасная валидация Compose, liveliness, список маршрутов без генерации, listeners, TLS и метаданные файлов авторизации. Точные безопасные HTTP endpoints фиксируются по проверенной конфигурации, а не выбираются по похожему имени.

Не запускать генерацию, login/refresh, общий `/health` или `/health/drain`. Не выводить `.env`, `auth.json`, базу панели, приватные ключи, полный `docker inspect` или раскрытый `docker compose config`.

Вывод формировать по allowlist полей. Редактирование секретов regex-заменой поверх полного raw stdout — только дополнительная защита, не основной механизм. Ограничить объём stderr, логов и тела ошибочного HTTP-ответа; не допускать утечки env или заголовков в tracebacks и argv.

Успешный ответ liveliness или наличие модели в списке маршрутов не доказывают модельную генерацию. Listener/TLS MTProto не доказывают вход Telegram-клиента. Итог честно показывает `not_run` для этих проверок; ручное клиентское подтверждение хранится отдельно от машинных наблюдений.

## 14. Проверки и порядок реализации

### P0: безопасный обычный backup

Сначала извлечь инвентарь, зафиксировать границы безопасности, реализовать read-only `inspect` и `plan`, затем job state/locking/idempotent submit, автономный backup и его финализатор, переносимую проверку и контролируемый fetch. Архивный worker используется как исходный материал, а не копируется без закрытия пробелов с Certbot/COMPLETE.

Для P0 обязательна тестовая процедура восстановления на изолированной VPS/VM: без этого проверены только создание и целостность архива, но не восстановимость. Полный пользовательский CLI restore может появиться в P1, однако проверка восстановления должна существовать уже до заявления о пригодности P0 для эксплуатации.

### P1: управляемый restore

Добавить `prepare`, `stage`, проверку mounts/digests/прав, восстановление Fail2ban и guarded `activate`. Автоматизацию Certbot включить после получения настоящих helper/units и испытаний их переноса. Не обобщать реализацию на неизвестные дистрибутивы.

### За пределами первой версии

Автоматический DNS cutover, финальное выключение source, полноценный rollback авторизации, изменение firewall, retention/prune, расписание периодических backup, автоматический boot-recovery и MCP-обёртка. При появлении MCP он только вызывает тот же CLI/ядро, а не содержит второй алгоритм.

### Приёмочные испытания

| Сценарий | Обязательный результат |
|---|---|
| Завершение локального агента/SSH после принятия job | Source-worker продолжает без модели; результат доступен по ID |
| Потеря ответа на `backup start`, повтор request ID | Не появляется второй backup |
| Одновременный backup или незавершённое восстановление прошлой job | Отказ до новых изменений |
| Ошибка tar, нехватка места, timeout или SIGKILL основного worker | Сохранена исходная причина; recovery выполняется; `COMPLETE` не выдаёт ложный успех |
| Docker не восстановил сервис / авария хоста | `recovery_required` либо `unknown/interrupted`; нет ложного успеха |
| Контейнер был остановлен до backup | Он остаётся остановленным; в частности, не запускается `telemt` |
| Активная lease/продление Certbot или гонка запуска | Остановка backup до копирования; cleanup не отключается |
| Новый mount/сервис, relay без воспроизводимого образа | Drift/error вместо неполной «успешной» копии |
| Подменён target, два alias на source, устаревший plan | Restore отклоняется до записи |
| Непустой target, конфликт volumes, частичная старая restore-job | Нет перезаписи без доказуемого продолжения той же операции |
| Пропущенный артефакт, неверный hash, symlink escape, special file | Отказ до извлечения в рабочие пути |
| Валидные ссылки Let's Encrypt, UID/GID, mode, ACL/xattrs | Восстановлены с разрешённой семантикой и проверены |
| UFW-архив содержит hooks/готовые команды | Они никогда не применяются к target |
| Источник всё ещё использует OAuth | Активация второй LiteLLM запрещена |
| Unit исчез после завершения | Долговечный отчёт читается; отсутствие доказательств не трактуется как успех |
| Секреты-«канарейки» в env, HTTP error, Compose stderr и файлах | Они отсутствуют в stdout/stderr/логах для агента |

Unit-тесты выполняются с fake adapters и синтетическими fixtures. Интеграционные проверки systemd/Docker/reboot выполняются на одноразовой VM, не на действующей VPS. Реальные OAuth-данные нельзя использовать для теста с двумя одновременно активными копиями; нужны заглушки или отдельно согласованная передача роли без параллельного использования.

### Критерий завершения преобразования

Агент способен выполнить обычный backup вызовами `plan -> start -> status -> verify`, ни разу не сочиняя shell-процедуру. Все изменения, восстановление и критерии успеха определены кодом и проверены сценариями отказа. Пользователь сохраняет контроль над scope, целевой машиной и переключением роли.

Экономию оценивать по реальным сессиям: входные/выходные токены, число вызовов модели, tool calls, ошибочные переходы, время остановки и доля успешных restore drills. Не обещать заранее произвольные проценты экономии.
