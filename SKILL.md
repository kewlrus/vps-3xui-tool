# vps-3xui

Область скилла: контейнеры, Compose, bind mounts, Docker volumes и перенос
данных этого стека. Критическая механика backup выполняется кодом
(`bin/vps3xui`), а не пошаговыми командами агента. Этот файл — короткий
протокол; синтаксис команд смотри в `bin/vps3xui --help`, а JSON-поля в схеме
манифеста, а не в копиях алгоритма здесь.

## Протокол вызова

Используй vps3xui для диагностики, backup и восстановления данного стека.
Сначала вызови inspect или plan. Изменения выполняй только после разрешения
владельца на конкретную машину и этап; наличие `--apply` его не заменяет.

Не переписывай worker и не выполняй пошаговый cold backup через модельный
канал, который будет остановлен. Перед запуском сообщи о downtime и сохрани
request/job ID. `accepted` означает только принятие задачи.

После восстановления связи читай `job status` и `backup verify`. Не объявляй
успех по доступности прокси или одному `COMPLETE`. При drift, конфликте,
неизвестном результате или `recovery_required` остановись и объясни ситуацию.

Restore не применяется к источнику. Не импортируй UFW, не меняй DNS и
авторизацию автоматически. Соблюдай отдельные условия активации target
и разрешённое исключение для Certbot guard.

Не выводи секреты. Не проводи генерацию и активные ACME/клиентские проверки
в рамках пассивной диагностики. Для архитектуры и ручного восстановления
читай соответствующие references только по необходимости.

## Команды P0

Поверхность (все команды поддерживают `--json` с одним объектом результата):

- `vps3xui inspect --host ALIAS --manifest FILE` — read-only инвентарь и drift.
- `vps3xui backup plan --host ALIAS --manifest FILE --out PLAN --ttl-minutes N`
  — построить привязанный к машине план с истечением.
- `vps3xui backup start --host ALIAS --manifest FILE --plan PLAN --request-id ID --apply`
  — зарегистрировать и запустить автономный backup.
- `vps3xui job status JOB_ID --host ALIAS` — достоверное состояние задачи.
- `vps3xui backup verify --host ALIAS --job JOB_ID --manifest FILE` — проверка на источнике.
- `vps3xui backup verify --directory DIR --manifest FILE` — проверка переносимой копии.
- `vps3xui backup fetch --host ALIAS --job JOB_ID --destination DIR --manifest FILE --apply`
  — контролируемо скачать секретную копию.
- `vps3xui job recover --host ALIAS --job JOB_ID --apply` — независимое восстановление
  сервисов для задачи в `recovery_required`/`unknown`.

Коды возврата сгруппированы: `0` успех, `2` контракт/аргументы, `3`
предусловие/конфликт (drift, устаревший план, конфликт request id, lock),
`4` выполнение, `5` проверка. Точные `error.code` и `--help` — источник истины.

## Установка и запуск

- Требуется только `python3` (стандартная библиотека, проверено на 3.9) плюс
  штатные OpenSSH, Docker/Compose, systemd и GNU tar на целевом хосте.
  Сторонние зависимости не требуются и не устанавливаются.
- Локальный CLI: `bin/vps3xui` (обёртка `python3 -m vps3xui.cli`).
  На VPS используется закреплённый release из `/opt/vps3xui/releases/<version>/`.
- Манифест: `config/manifest.schema.json` — схема, `config/manifest.example.json`
  — пример снятого снимка. Пример `approved=false` и предназначен только как
  образец: рабочий манифест собирается после свежего `inspect`, проверяется и
  утверждается владельцем до любого `--apply`.
- Весь бэкап считается секретным целиком, независимо от флагов `sensitive` в
  манифесте: `sensitive` — только подсказка для отчётности, а не граница
  доступа. Отдельный формат секретов не нужен.

## Границы P0

- По умолчанию всё read-only. Любое изменяющее действие требует `--apply`
  и явного разрешения владельца на названную машину.
- Вне scope P0: `restore`/активация на цели, импорт UFW, изменение DNS,
  prune/retention, архивирование образов, режим финального копирования,
  деплой и установка пакетов. Всё это либо отдельное согласование, либо P1+.
- UFW переносится только как reference-артефакт и никогда не применяется.
- Certbot: неизвестный планировщик или hook — конфликт. Оригинальное состояние
  таймера/сервиса сохраняется и восстанавливается точно; guard активируется
  только по отдельному доверенному контракту.
- telemt не запускается, если не был запущен до backup.

## Ограничения доказательств

- **VM restore drill НЕ ВЫПОЛНЕН.** Нет одноразовой Linux VM в этой среде.
  Портативная часть (`scripts/portable_restore_drill.py`, вызывается из
  `scripts/vm-restore-drill.sh`) прогоняется локально на синтетических fixtures
  и проверяет: полную копию принимает, частичную отклоняет, отдельные
  destinations для named volumes и обоих Fail2ban-каталогов, mode 0600 у
  восстановленного секрета, относительную ссылку Let's Encrypt внутри дерева,
  неприменение UFW, отсутствие `COMPLETE` после SIGKILL и отсутствие ложного
  успеха finalizer. VM-часть (реальные Docker volumes, create-stopped container,
  bounded systemd worker/finalizer с SIGKILL/timeout/потерей транспорта, GNU tar
  metadata round-trip) остаётся `NOT RUN` без одноразовой цели и печатает exit 3.
  P0 нельзя называть пригодным для эксплуатации до прохождения VM-части.
- Живая готовность намеренно заблокирована: `agent-relay` в манифесте числится
  в `pending_approval` и обязан быть подтверждён свежим read-only `inspect`;
  исходник доверенного `certbot-http01-guard` отсутствует. Пример манифеста
  не утверждён и содержит пустой `trusted_files`/`hook_fingerprints`; утверждённый
  манифест обязан закрепить полный trust-набор (guard, его маркер, cleanup-юниты,
  dropin, renewal-файл, права guard-хелпера `mode`/`uid`/`gid`) и все разрешённые
  hook-команды, иначе drift fail-closed.
- Реальная VPS в рамках P0 не опрашивалась; секреты и OAuth не читались,
  использовались синтетические fixtures и канарейки.
