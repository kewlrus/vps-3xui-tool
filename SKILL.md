# Приложения vps-3xui

Описывай текущее устройство приложений и нужное действие, без истории исправлений.
Область скилла: контейнеры, Compose, конфигурации, bind mounts, Docker volumes,
клиентские подключения и перенос данных. Установка Docker Engine и плагина
Docker Compose на новой VPS, включая необходимые зависимости и запуск сервиса,
входит в развёртывание из backup, если Docker ещё не установлен.
Установка Certbot и восстановление автоматического продления через его
systemd-таймер на новой VPS также входят в развёртывание из backup.
Чтение состояния UFW и backup его конфигурации также входят в scope.
Установка ОС, настройка железа, общее обслуживание системных библиотек
и изменение правил firewall сюда не входят.

## Как пользоваться

- Для диагностики и понимания стека читать [текущую конфигурацию](references/apps.md).
- Для backup или развёртывания на чистой VPS обязательно читать
  [резервное копирование и восстановление](references/backup-restore.md).
  Полноценный перенос выполняется из согласованной копии приложений:
  этот скилл не содержит пользовательских ключей, базы клиентов или OAuth-токенов.
- Обновляя скилл, заменять устаревшие значения текущими. Не добавлять хронику,
  переписку, старые ошибки, неактивные варианты конфигурации и журналы.

## Границы действий

На действующей VPS разрешены чтение и подготовка изменений. Без явного
разрешения не создавать архивы, не менять файлы/настройки, не перезапускать
контейнеры, не обновлять образы и не выполнять изменяющие API-запросы.
Просьба обновить этот скилл разрешает править только его локальные файлы.

Агент получает ответы модели через этот же LiteLLM/Caddy. Их остановка прерывает
его работу. Нельзя выполнять холодный backup пошаговыми вызовами инструментов
с расчётом на следующую команду агента. До остановки подготовить и проверить
полную автономную задачу на VPS с ограничением времени, журналом и восстановлением
контейнеров через systemd ExecStopPost; см. процедуру backup. Не запускать её
интерактивно через зависимый от сессии SSH-процесс. После возвращения прокси
проверить результат задачи; не считать восстановление подключения доказательством backup.
Финальное выключение источника допустимо только после перехода на независимый
канал модели или передачи дальнейших действий пользователю.

Разрешение развернуть приложения на новой VPS относится к названной целевой
машине; остановку/backup источника и переключение доменов согласовывать отдельно,
если они ещё не разрешены. Команды в справке сами по себе не дают разрешения.

При развёртывании backup НЕЛЬЗЯ применять правила UFW: это делает пользователь.
Архив UFW переносится только как справочный материал, отдельно от данных приложений.
Не заменять /etc/ufw и /etc/default/ufw на цели, не включать/выключать/перезагружать
UFW и не импортировать его правила через другие инструменты или startup hooks.
Разрешение на развёртывание Docker-приложений не отменяет этого запрета.
Отдельное разрешённое исключение при восстановлении: установка и активация
certbot-http01-guard из backup, временный доступ TCP/80 только во время продления,
аварийная очистка и перезапуск 3x-ui после успешного продления. Разрешение входит
в backup и перепривязывается к machine-id новой VPS без повторного согласования.
Оно не разрешает импорт остальных правил UFW или постоянное открытие порта.

При диагностике не запускать генерацию, login/refresh токенов или /health:
они могут расходовать квоту либо менять авторизацию. Не вызывать /health/drain.
Не выводить секреты из .env, auth.json, БД панели, приватных ключей и журналов.
Не печатать полный docker inspect или раскрытый docker compose config.
Для auth.json достаточно метаданных; не импортировать Authenticator ради проверки.

## Доступ

Действующая VPS: root@185.73.124.38, SSH alias vps-3xui, порт 22.
Использовать существующий ключ и проверку известного host key:

```bash
ssh -o BatchMode=yes -o StrictHostKeyChecking=yes -o UpdateHostKeys=no \
  -o ControlMaster=no -o ControlPath=none -o ConnectTimeout=10 \
  vps-3xui 'docker ps -a'
```

Новый сервер должен иметь отдельный SSH alias и проверенный host key.
Не перенаправлять alias источника до завершения переноса.

## Что работает и зачем

Конфигурации, mounts и состояние контейнеров сверены чтением 20.09.2026.
Работу Claude по подписке и MTProto подтвердил владелец; каждый модельный
маршрут генерацией не проверялся.

| Компонент | Состояние | Назначение |
|---|---|---|
| litellm | running | Общий LLM-шлюз для Claude Code и Codex |
| caddy | running | HTTPS для шлюза и страница прикрытия MTProto |
| 3xui_app | running | Панель, Xray и отдельный процесс MTProto/mtg |
| telemt | exited | Не используется рабочей схемой; по умолчанию не переносить и не запускать |

LLM: клиент -> kewlllm.duckdns.org:443 -> Caddy -> litellm:4000 -> провайдер.
Telegram: клиент -> kewlnotes.duckdns.org:8443 -> mtg внутри 3x-ui -> Telegram.
HTTPS-прикрытие MTProto использует Caddy на 127.0.0.1:443.

## Инварианты

- Ключ шлюза: X-Litellm-Api-Key: Bearer <ключ LiteLLM> у обоих клиентов.
  Authorization Claude сохраняется для OAuth подписки; не подменять его ключом шлюза.
- Codex использует Responses и маршруты chatgpt/, а авторизация ChatGPT хранится
  в серверном томе. Не менять провайдера на openai/ при обслуживании Claude.
- LiteLLM:4000 не опубликован на хосте. Проверять его из контейнера;
  адрес localhost:4000 на самой VPS для этого не подходит.
- Сохранять имена Compose-проектов llmproxy и panel, имена томов и пути bind mounts.
  Для panel обязателен рабочий каталог /root/panel из-за $PWD в Compose.
- MTProto обслуживает 3x-ui, не остановленный telemt; Caddy занимает 443.
- Caddy продлевает свои сертификаты сам. Для kewlsub.duckdns.org нужен
  отдельный Certbot на хосте и certbot.timer; одного /etc/letsencrypt недостаточно.
  На действующей VPS отдельно разрешены hooks временного доступа к 80/tcp
  с аварийной очисткой и перезапуска 3x-ui после продления (см. apps.md).
  Разрешение на их активацию при переносе входит в backup; порядок и проверки
  описаны в references/backup-restore.md. Остальные правила UFW не применять.
- YAML требует перечитывания процессом. Изменения env/mounts/image требуют
  пересоздания контейнера; обычный restart их не применяет.
- Не переносить весь /var/lib/docker и не архивировать Docker-образы.
  Backup содержит конфигурации, данные mounts и ссылки на образы; при восстановлении
  образы скачиваются из registry через интернет. Не использовать down -v или prune.

## Проверки без генерации

```bash
docker ps -a --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}'
docker inspect litellm --format '{{json .Mounts}}'
docker inspect 3xui_app --format '{{json .Mounts}}'
ufw status verbose
docker compose -p llmproxy --project-directory /opt/llmproxy \
  -f /opt/llmproxy/docker-compose.yaml config --quiet
curl --fail --silent --show-error --max-time 15 \
  https://kewlllm.duckdns.org/health/liveliness
```

Список загруженных маршрутов, включая wildcard Claude; ключ не попадает в argv:

```bash
docker exec -i litellm python -B - <<'PY'
import json
import os
from pathlib import Path
import urllib.request
import yaml

config = yaml.safe_load(Path("/app/config.yaml").read_text())
header = config.get("general_settings", {}).get("litellm_key_header_name", "Authorization")
request = urllib.request.Request(
    "http://127.0.0.1:4000/v1/models?return_wildcard_routes=true",
    headers={header: "Bearer " + os.environ["LITELLM_MASTER_KEY"]},
)
with urllib.request.urlopen(request, timeout=15) as response:
    print(response.status, [item["id"] for item in json.load(response)["data"]])
PY
```

Наличие маршрута не доказывает доступность модели для аккаунта.
Для MTProto проверять listener :8443, HTTPS-прикрытие и подключение реального
Telegram-клиента отдельно. Успешный HTTPS-запрос не проверяет secret Telegram.
Журналы читать с --since/--tail, очищая секреты и пользовательский контент.
